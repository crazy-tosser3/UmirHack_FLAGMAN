# Admin API Documentation

**Версия:** 1.0  
**Base URL:** `/api/v1/admin`  
**Формат:** JSON (`application/json`)  
**Назначение:** управление пользователями и ролями, справочниками, системными настройками и аудитом административных действий.

> Это проектный контракт для MVP. Эндпоинты, не определённые в исходном API-контракте, являются предлагаемым расширением.

## 1. Общие правила

- Все запросы выполняются по HTTPS.
- Тела запросов и ответов используют JSON в UTF-8.
- Идентификаторы сущностей — UUID.
- Даты и время передаются в ISO 8601 с часовым поясом; внутри системы рекомендуется UTC.
- Для списков рекомендуется пагинация `page` и `limit`.
- Все административные эндпоинты требуют действительный access token и роль `admin`. Проверка роли выполняется на сервере для каждого запроса.
- Скрытие кнопок в интерфейсе не заменяет серверную авторизацию.

Формат пагинации:

```json
{
  "items": [],
  "page": 1,
  "limit": 20,
  "total": 0
}
```

## 2. Роли и доступ

Поддерживаемые роли:

- `admin` — управление пользователями, ролями и административными настройками.
- `manager` — работа с поставками, остатками, партиями, заказами и стоп-листом.
- `employee` — доступ только к разрешённым операциям.

Правила:
- Назначение неизвестной роли возвращает `400 VALIDATION_ERROR`.
- Нельзя заблокировать или понизить роль последнего активного администратора.
- Изменения ролей, статусов аккаунтов и настроек записываются в аудит.

## 3. Пользователи

### 3.1. `GET /users`

Возвращает список пользователей.

Query-параметры: `page`, `limit` (1–100), `search` (имя или email), `role` (`admin`, `manager`, `employee`), `status` (`active`, `blocked`).

Пример: `GET /api/v1/admin/users?page=1&limit=20&role=manager&status=active`

**`200 OK`**

```json
{
  "items": [
    {
      "id": "0190a100-0000-4000-8000-000000000001",
      "name": "Иван Петров",
      "email": "ivan@example.com",
      "role": "manager",
      "status": "active",
      "createdAt": "2026-10-09T10:00:00Z",
      "updatedAt": "2026-10-09T10:00:00Z"
    }
  ],
  "page": 1,
  "limit": 20,
  "total": 1
}
```

Пароли, password hash, refresh tokens и другие секреты не возвращаются.

### 3.2. `POST /users`

Создаёт пользователя. Рекомендуется отправлять приглашение или одноразовую ссылку для установки пароля, а не передавать постоянный пароль администратора.

Тело запроса:

```json
{
  "name": "Иван Петров",
  "email": "ivan@example.com",
  "role": "manager"
}
```

Поля: `name` (обязательно), `email` (обязательно, уникальный после нормализации), `role` (обязательно: `admin`, `manager`, `employee`).

**`201 Created`**

```json
{
  "id": "0190a100-0000-4000-8000-000000000001",
  "name": "Иван Петров",
  "email": "ivan@example.com",
  "role": "manager",
  "status": "active",
  "createdAt": "2026-10-09T10:00:00Z"
}
```

Если требуется подтверждение приглашения, можно использовать статус `pending`; этот процесс необходимо определить отдельно.

Ошибки: `400 VALIDATION_ERROR`, `409 USER_ALREADY_EXISTS`.

### 3.3. `GET /users/{userId}`

Возвращает профиль пользователя.

**`200 OK`**

```json
{
  "id": "0190a100-0000-4000-8000-000000000001",
  "name": "Иван Петров",
  "email": "ivan@example.com",
  "role": "manager",
  "status": "active",
  "createdAt": "2026-10-09T10:00:00Z",
  "updatedAt": "2026-10-09T10:00:00Z"
}
```

Ошибки: `400 VALIDATION_ERROR`, `404 USER_NOT_FOUND`.

### 3.4. `PATCH /users/{userId}`

Изменяет профиль. Допустимые поля: `name`, `email`. Роль и статус меняются отдельными эндпоинтами.

```json
{
  "name": "Иван Петров"
}
```

**`200 OK`** — обновлённый профиль в формате `GET /users/{userId}`.

Ошибки: `400 VALIDATION_ERROR`, `404 USER_NOT_FOUND`, `409 USER_ALREADY_EXISTS`.

### 3.5. `PATCH /users/{userId}/role`

Назначает роль.

```json
{
  "role": "employee"
}
```

**`200 OK`**

```json
{
  "id": "0190a100-0000-4000-8000-000000000001",
  "role": "employee",
  "updatedAt": "2026-10-09T11:00:00Z"
}
```

Ошибки: `400 VALIDATION_ERROR`, `404 USER_NOT_FOUND`, `409 LAST_ADMIN_REQUIRED`.

### 3.6. `PATCH /users/{userId}/status`

Активирует или блокирует аккаунт. Допустимые значения: `active`, `blocked`.

```json
{
  "status": "blocked"
}
```

**`200 OK`**

```json
{
  "id": "0190a100-0000-4000-8000-000000000001",
  "status": "blocked",
  "updatedAt": "2026-10-09T11:00:00Z"
}
```

При блокировке refresh tokens пользователя должны быть отозваны. Уже выданный access token может действовать до истечения срока, если не реализована немедленная проверка статуса.

Ошибки: `400 VALIDATION_ERROR`, `404 USER_NOT_FOUND`, `409 LAST_ADMIN_REQUIRED`.

### 3.7. `POST /users/{userId}/password-reset`

Инициирует сброс пароля. Новый пароль и секретный токен сброса в ответе не возвращаются.

**`202 Accepted`**

```json
{
  "status": "accepted"
}
```

Ошибка: `404 USER_NOT_FOUND`.

## 4. Справочник ингредиентов

В базовом контракте чтение ингредиентов предусмотрено, а создание и изменение не включены. Следующие эндпоинты — административное расширение.

### 4.1. `POST /ingredients`

Создаёт ингредиент.

```json
{
  "name": "Моцарелла",
  "unit": "g"
}
```

Допустимые базовые единицы: `g`, `ml`, `pcs`.

**`201 Created`**

```json
{
  "id": "0190a101-0000-4000-8000-000000000001",
  "name": "Моцарелла",
  "unit": "g"
}
```

Ошибки: `400 VALIDATION_ERROR`, опционально `409 INGREDIENT_ALREADY_EXISTS`, если введено правило уникальности названия.

### 4.2. `PATCH /ingredients/{ingredientId}`

Изменяет название или базовую единицу.

```json
{
  "name": "Моцарелла для пиццы"
}
```

Допустимые поля: `name`, `unit`.

Изменение `unit` после появления рецептов или складских движений может нарушить смысл исторических количеств. Рекомендуется запрещать его без отдельной миграции и пересчёта.

**`200 OK`**

```json
{
  "id": "0190a101-0000-4000-8000-000000000001",
  "name": "Моцарелла для пиццы",
  "unit": "g"
}
```

Ошибки: `400 VALIDATION_ERROR`, `404 INGREDIENT_NOT_FOUND`, `409 INGREDIENT_IN_USE`.

## 5. Блюда и рецепты

### 5.1. `POST /dishes`

Создаёт блюдо и его рецепт. Количество ингредиента указывается на одну порцию и должно быть больше нуля.

```json
{
  "name": "Пицца Маргарита",
  "isActive": true,
  "ingredients": [
    {
      "ingredientId": "0190a101-0000-4000-8000-000000000001",
      "quantity": 120
    },
    {
      "ingredientId": "0190a101-0000-4000-8000-000000000002",
      "quantity": 80
    }
  ]
}
```

**`201 Created`**

```json
{
  "id": "0190a102-0000-4000-8000-000000000001",
  "name": "Пицца Маргарита",
  "isActive": true,
  "ingredients": [
    {
      "ingredientId": "0190a101-0000-4000-8000-000000000001",
      "quantity": 120,
      "unit": "g"
    },
    {
      "ingredientId": "0190a101-0000-4000-8000-000000000002",
      "quantity": 80,
      "unit": "g"
    }
  ]
}
```

Создание блюда и всех строк рецепта выполняется атомарно.

Ошибки: `400 VALIDATION_ERROR`, `404 INGREDIENT_NOT_FOUND`.

### 5.2. `PATCH /dishes/{dishId}`

Изменяет название, активность и/или рецепт. Если поле `ingredients` передано, оно **полностью заменяет** текущий состав; если не передано — состав остаётся без изменений.

```json
{
  "name": "Маргарита",
  "ingredients": [
    {
      "ingredientId": "0190a101-0000-4000-8000-000000000001",
      "quantity": 130
    }
  ]
}
```

**`200 OK`** — обновлённое блюдо с полным составом.

Ошибки: `400 VALIDATION_ERROR`, `404 DISH_NOT_FOUND`, `404 INGREDIENT_NOT_FOUND`.

Изменение рецепта применяется к будущим заказам. Для исторической точности заказ должен хранить фактическое списание и, при необходимости, снимок рецепта на момент оформления.

## 6. Ручная доступность блюда

### `PATCH /dishes/{dishId}/availability`

Устанавливает или снимает ручную блокировку. Она хранится отдельно от автоматически рассчитанной доступности по остаткам.

Заблокировать:

```json
{
  "manualBlocked": true,
  "reason": "Временно снято с продажи"
}
```

Снять ручную блокировку:

```json
{
  "manualBlocked": false
}
```

**`200 OK`**

```json
{
  "dishId": "0190a102-0000-4000-8000-000000000001",
  "manualBlocked": true,
  "reason": "Временно снято с продажи",
  "updatedAt": "2026-10-09T11:30:00Z"
}
```

Снятие ручной блокировки не гарантирует доступность блюда: система должна проверить пригодные складские остатки.

Ошибки: `400 VALIDATION_ERROR`, `404 DISH_NOT_FOUND`.

## 7. Настройки системы

### 7.1. `GET /settings`

**`200 OK`**

```json
{
  "expiryWarningHours": 48,
  "offers": {
    "defaultLimit": 10,
    "minimumPriority": 30
  },
  "updatedAt": "2026-10-09T11:30:00Z"
}
```

### 7.2. `PATCH /settings`

Частично изменяет настройки. Неизвестные поля отклоняются.

```json
{
  "expiryWarningHours": 24,
  "offers": {
    "defaultLimit": 10,
    "minimumPriority": 40
  }
}
```

Правила валидации:
- `expiryWarningHours` — целое число больше нуля.
- `defaultLimit` — целое число от `1` до `100`.
- `minimumPriority` — число от `0` до `100`.

**`200 OK`** — полный обновлённый объект настроек.

Изменения атомарны и фиксируются в аудите. Секреты интеграций не должны возвращаться этим endpoint.

Ошибка: `400 VALIDATION_ERROR`.

## 8. Аудит

### `GET /audit-logs`

Возвращает историю административных действий.

Query-параметры: `page`, `limit` (1–100), `actorId` (UUID), `action`, `targetId` (UUID), `from`, `to` (datetime).

Пример: `GET /api/v1/admin/audit-logs?action=user.role_changed&page=1&limit=20`

**`200 OK`**

```json
{
  "items": [
    {
      "id": "0190a103-0000-4000-8000-000000000001",
      "actorId": "0190a100-0000-4000-8000-000000000010",
      "action": "user.role_changed",
      "targetType": "user",
      "targetId": "0190a100-0000-4000-8000-000000000001",
      "createdAt": "2026-10-09T11:00:00Z",
      "requestId": "req-0190a104",
      "metadata": {
        "oldRole": "manager",
        "newRole": "employee"
      }
    }
  ],
  "page": 1,
  "limit": 20,
  "total": 1
}
```

Рекомендуемые типы действий:
- `user.created`
- `user.updated`
- `user.role_changed`
- `user.status_changed`
- `user.password_reset_requested`
- `ingredient.created`
- `ingredient.updated`
- `dish.created`
- `dish.updated`
- `dish.manual_availability_changed`
- `settings.updated`

Записи аудита не изменяются через публичный API. Не записывайте в `metadata` пароли, токены или другие секреты.

Ошибка: `400 VALIDATION_ERROR`.

## 9. Состояние сервиса

### `GET /health`

Технический endpoint для проверки приложения и его зависимостей.

**`200 OK`**

```json
{
  "status": "ok",
  "checks": {
    "database": "ok"
  },
  "timestamp": "2026-10-09T11:30:00Z"
}
```

При неготовности сервиса допустим `503 Service Unavailable` с минимальной информацией. Не возвращайте строки подключения, внутренние адреса, имена пользователей БД и секреты. Endpoint ограничивается сетевыми правилами или отдельной политикой доступа; публичный liveness check лучше вынести из `/admin`.

## 10. Ошибки API

Рекомендуемый единый формат:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Запрос содержит некорректные данные",
    "details": [
      {
        "field": "role",
        "reason": "unsupported_value"
      }
    ],
    "requestId": "req-0190a104"
  }
}
```

| HTTP | Код / значение | Причина |
|---|---|---|
| `400` | `VALIDATION_ERROR` | Некорректные поля, UUID или параметры |
| `401` | `UNAUTHORIZED` | Нет действительной аутентификации |
| `403` | `FORBIDDEN` | Нет роли `admin` |
| `404` | `USER_NOT_FOUND`, `DISH_NOT_FOUND`, `INGREDIENT_NOT_FOUND` | Сущность не найдена |
| `409` | `USER_ALREADY_EXISTS` | Email уже зарегистрирован |
| `409` | `LAST_ADMIN_REQUIRED` | Операция оставит систему без активных администраторов |
| `409` | `INGREDIENT_IN_USE` | Изменение единицы несовместимо со связанными данными |
| `500` | `INTERNAL_SERVER_ERROR` | Необработанная внутренняя ошибка |

Не возвращайте stack trace и внутренние детали реализации.

## 11. Безопасность и целостность

1. Каждый административный endpoint проверяет access token и роль `admin` на сервере.
2. Нельзя понизить роль или заблокировать последнего активного администратора.
3. Email уникален после нормализации.
4. Пароли хранятся только в виде безопасных хешей; API не возвращает пароль или хеш.
5. При блокировке аккаунта refresh tokens отзываются.
6. Изменение рецепта выполняется атомарно.
7. Базовую единицу ингредиента нельзя менять без согласованного пересчёта связанных данных.
8. Ручная блокировка блюда не перезаписывается автоматическим пересчётом стоп-листа.
9. Изменения ролей, статусов, справочников и настроек фиксируются в аудите.
10. Аудит не содержит секреты.
11. Все операции валидируют входные данные и используют единый формат ошибок.
12. Health checks не раскрывают чувствительную информацию об инфраструктуре.

## Рекомендуемый порядок реализации

1. Проверка роли `admin` на сервере.
2. Просмотр и создание пользователей.
3. Назначение ролей и блокировка аккаунтов с защитой последнего администратора.
4. CRUD ингредиентов, блюд и рецептов, если администратор управляет каталогом.
5. Аудит административных изменений.
6. Настройки системы и ручная доступность блюд.
7. Сброс пароля и технические health checks.
